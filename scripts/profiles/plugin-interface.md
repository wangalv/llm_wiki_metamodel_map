# Profile plugins (advanced)

**This vault doesn't need this page.** Its rules come entirely from `Schema/wiki-config.json` and `scripts/profiles/togaf-core/togaf-core-profile.md`. Read on only if the configuration can't express what you need and you want to add Python code — for example a converter that turns a raw document format into a Markdown source note.

A profile adapts the domain-agnostic core (`scripts/wiki_tool.py`) to one business domain, such as legislation, research papers or compliance policies.

- **Choosing a profile:** set `"profile": "<name>"` in `Schema/wiki-config.json`.
- **Note kinds, fields, statuses and naming:** these also live in `wiki-config.json`.
- **Plugins:** this folder holds the plugin code, one subfolder per profile.

```
scripts/profiles/<name>/
├── <name>-profile.md  what the profile is for, its kinds and conventions (unique filename: Obsidian links by name)
├── rules.py         optional: extra lint rules
├── generators.py    optional: files generated by `build`
└── converters.py    optional: raw document → source note converters
```

Every plugin file is optional. A profile folder with none of them is valid. The `default` profile doesn't need a folder at all.

## Plugin interface

Each plugin receives:

| Argument | What it is |
|---|---|
| `v` | The `Vault` object: `v.files()`, `v.note(rel)`, `v.resolve(target)`, `v.compiled_paths()`, `v.source_paths()`, `v.cfg` (the config) |
| `core` | The `wiki_tool` module itself, so plugins can reuse its helpers: `split_frontmatter`, `body_links`, `headings`, `as_list`, `link_target`, `is_date`, `mask_code`, … |

### `rules.py`

Check the declarative rule library first (`rules` in `Schema/wiki-config.json`, see `Schema/command-reference.md#rules`). It covers:
- anchored citations
- labels that must match anchors
- coverage of source headings
- cited table rows
- verbatim quotes
- unique field combinations
- filename patterns

Write Python rules only for checks those can't express.

```python
def compiled_rules(v, add, core):
    """Extra checks on Wiki notes, run at the end of `wiki_tool.py lint`."""
    for rel in v.compiled_paths():
        note = v.note(rel)
        ...
        add("error", "X1", rel, "message", line)   # level: "error" | "warn"

def source_rules(v, add, core):
    """Extra checks on Raw sources, run at the end of `wiki_tool.py source-lint`."""
```

Use finding codes that don't clash with the core codes (F, S, L, N, C, K, M). A good choice is a profile prefix plus a number, e.g. `LG1` for legislation. Document each code in `<name>-profile.md` and in `Schema/lint-checklist.md`.

### `generators.py`

Check the declarative generator library first (`generators` in `Schema/wiki-config.json`, see `Schema/command-reference.md#generators`). It covers:
- heading outlines
- term lists quoted from the source
- tables of notes
- Obsidian Bases views

Write Python generators only for output those can't produce.

```python
def generate(v, core):
    """Return {vault-relative path: file content}. Paths must be under Wiki/."""
    return {"Wiki/Acts/Some Act — Structure.md": "..."}
```

- **When it runs:** `build` runs generators first and writes their files. Then it builds the catalog and indexes, so generated notes are included.
- **Staleness:** `lint` reports any generated file that is out of date (K1).
- **Generated notes follow the normal rules.** A file generated inside a kind folder (e.g. `Wiki/Acts/`) is treated as a compiled note, so it must have valid frontmatter and cite its sources, like any other note.
- **Deterministic output:** generators must produce the same output for the same inputs. Don't include timestamps or random order.

### `converters.py`

```python
def nsw_legislation(src, out, core):
    """NSW Legislation web-page text → source note with section headings."""
    ...
    out.write_text(markdown, encoding="utf-8")
    return f"wrote {out}"

CONVERTERS = {"nsw-legislation": nsw_legislation}
```

Run a converter with:

```bash
python3 scripts/wiki_tool.py convert nsw-legislation input.txt --output Raw/Sources/<name>.md
```

Use `convert --list` to see the available converters. A converter writes a new source note. The core rules still apply afterwards: from then on, the Raw file is read-only.
